# KIKO 근거·평가·변경 규칙

2026-09-28. 6~9월 에이전트 작업에서 실제로 틀렸던 사례를 규칙으로 정리했다. 괄호 안은 계기가 된 사건이다.

## 1. 근거

- 코드, DB, 로그, 커밋으로 확인한 것만 사실로 쓴다. 확인하지 못한 내용은 "확인 못 함"으로 표시하고 보류한다.
- 설정값은 `app/core/config.py` 기본값이 아니라 배포된 값으로 확인한다. dev-ai 컨테이너의 env(`docker exec ai-server env`)가 기준이다. (8/23: 기본값 `nova-lite`만 보고 실제 에이전트 모델 `claude-haiku-4-5`를 잘못 답함)
- "적재 안 됨", "배치 안 돎" 같은 부정 판단은 DB를 직접 조회한 뒤에만 말한다.

## 2. 수치와 평가

- 수치에는 조건을 함께 적는다: 표본 수, 측정 날짜, 커밋, 모델, 채점 방식(사람 / LLM-as-judge / 규칙), 평가셋 출처(자체 제작 여부).
- 상한값, 커버리지, 정확도를 구분한다.
  - 정답 라벨을 입력으로 넣고 잰 값은 "상한"이다. (9/28: 속성정렬 rerank fit 0.38→0.83은 `case["expected"]`를 타깃으로 넣은 상한값)
  - 태그가 붙은 상품 비율은 "커버리지"이지 정확도가 아니다. (9/28: 무드 98%는 커버리지, 규칙 게이트 통과분은 77.8%)
- 평가 스크립트와 데이터셋은 반드시 저장소(`tests/eval/`, `scripts/goldenset/`)에 커밋한다. 컨테이너 `/tmp`나 로컬에만 두지 않는다. (9/28: `routing_eval`이 저장소에 없어 9/7 세션 기록에서 복원, #303)
- 결과 파일(`tests/eval/*_results.json`은 gitignore)에는 커밋 SHA, 모델, 날짜를 남기고, 문서에 인용할 결과는 PR 설명이나 문서에 조건과 함께 옮긴다. (가드레일 6/6 결과 파일에 모델 기록이 없어 재실행)
- 측정 전에 채점기를 샘플로 검수한다. 채점 결과 몇 건을 직접 열어 판정이 맞는지 본다. (9/28: routing e2e 측정 도구 결함 3건: 세션 언어 기본값 en으로 전 응답 영어, 자기소개 "style picks"를 거짓말로 오채점, 재실행 시 노출 dedupe로 카드 0장)
- 같은 모델이 자기 응답을 채점하지 않게 한다. 봇과 judge 모델을 다르게 둔다.

## 3. 버그와 수정

- 버그를 주장할 때는 운영 데이터에서 발생 빈도를 먼저 센다(`ai.log_conversation_event`). (9/24 #295: `evaluator_run` 70건 중 38건이 직전 검색 결과를 채점)
- 회귀 테스트는 수정 전 코드에서 실패하는지 확인한다. 통과만 확인하면 그 테스트가 버그를 잡는지 알 수 없다.

## 4. PR과 배포

- Claude는 PR 생성까지 한다. 머지는 사람이 검토하고 한다. `dev` 머지가 곧 dev 자동 배포(`deploy-dev.yml`)이기 때문이다.
- 운영 env 변경(`/home/ec2-user/env/.env`)은 사람이 확인한 뒤 `docker compose up -d ai-server`로 재생성한다. `docker restart`는 env를 다시 읽지 않는다.
- 다른 팀원 담당 영역(백엔드 앱, 크롤러, 임베딩 인프라)을 바꾸는 PR은 설명에 영향 범위를 적고 담당자에게 공유한다.

## 5. 문서

- 설계 문서, 포트폴리오, 슬라이드의 수치는 게시 전에 `kiko-doc-audit` 스킬(또는 `doc-auditor` 에이전트)로 코드·DB 대조 감사를 거친다. 글을 쓴 에이전트가 스스로 검수를 대신하지 않는다.
- 관련 스킬: `kiko-eval`(평가 재현), `kiko-ops-trace`(운영 데이터로 확인).
